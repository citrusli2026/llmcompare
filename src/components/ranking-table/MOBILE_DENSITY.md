# 移动端信息密度分析（MobileCard 改造方案）

> **背景**：LLMCompare `/models` 页面在 375–393px 移动端首屏只能看到 3–4 张完整卡片。
> 目标：在不修改数据层 / 桌面端体验的前提下，提升移动端浏览效率（更多模型可见 + 信息更清晰）。

---

### 1.2 当前 MobileCard 高度测量

`src/components/ranking-table/mobile-card.tsx` 当前结构（自上而下）：

```
┌─ p-3 (12) ───────────────────────┐
```

## 2. 方案矩阵

> 评分：首屏可见数 = iPhone 14/15 Pro（852px）的 240px 折算；信息密度按"能在不展开情况下读到的指标数"。

### 方案 A：紧凑单行卡（Compact Row）

- **核心思路**：将 logo + 名字 + 智能分（大数字）+ 价格压缩到一行；元信息（公司/日期/type）退到次行；移除独立指标网格。
- **首屏可见**：**4.5–5.5 张**（卡片高 90–100px）
- **信息密度**：每卡可见 4 项（智能、价格、类型、公司/日期）；点击进入详情看全部
- **浏览/搜索/对比**：浏览 ↑↑、搜索 →、对比 →
- **实现难度**：**小**（重写 MobileCard 内部 JSX ~80 行）
- **代码改动**：`mobile-card.tsx`（-50/+80）、`models/{zh,en}.json` 新增 ~3 keys
- **风险点**：指标密度下降（看不到 tokens/coding/agentic），需要靠详情页/排序补回

### 方案 B：超紧凑列表（Ultra-Compact List）

- **核心思路**：类 GitHub Issues 风格的单行行；只显示排名 + 名字 + 智能分；其他全进详情。
- **首屏可见**：**6–7 张**（卡片高 56–64px）
- **信息密度**：每卡 2 项（智能、是否开源）
- **浏览/搜索/对比**：浏览 ↑↑↑、搜索 ↑、对比 ↓（勾选目标变小）
- **实现难度**：**小**（重写更激进）
- **风险点**：对比按钮从 44×44 缩到 28×28，触摸目标过小（WCAG 44×44 失败）

### 方案 C：默认折叠 + 点击展开（Accordion Card）

- **核心思路**：默认显示主指标（智能 + 价格 + 类型）；点击卡片展开显示次指标（tokens/coding/agentic + 完整元信息 + 公司）。
- **首屏可见**：**3.5–4.5 张**（折叠态 100–110px）/ **2 张**（展开态 180–200px）
- **信息密度**：折叠时中等、展开时极高
- **浏览/搜索/对比**：浏览 ↑、搜索 →、对比 →（勾选始终可见）
- **实现难度**：**中**（需要受控展开状态 + 平滑过渡）
- **代码改动**：`mobile-card.tsx` 重构 ~120 行 + `useState` 提升到父组件（避免每卡独立状态丢失）
- **风险点**：状态需要持久化到 URL（否则刷新/翻页丢失）；展开时整页布局抖动

### 方案 D：横向滑动卡（Horizontal Swipe Indicators）

- **核心思路**：每张卡固定 ~100px 高；指标行做成横向 swipe 容器，水平滑动切换不同指标视图。
- **首屏可见**：**3.5–4.5 张**（卡片 100–110px）
- **信息密度**：理论无限（每个指标一个 slide），但实际发现成本高
- **实现难度**：**中**（需要 touch handling + 滚动指示器）
- **风险点**：用户不一定发现能滑动；与列表的"垂直浏览"心智模型冲突

### 方案 E：表格化横向滚动（Horizontal Table）

- **核心思路**：把桌面端 table 套到 mobile 上，加 `overflow-x-auto`，水平滑动看列。
- **首屏可见**：**2.5–3 张**（行高 ~140–160px 不变）
- **信息密度**：桌面端级别的所有列
- **实现难度**：**小**（复用桌面行组件，加 `overflow-x`）
- **风险点**：水平滚动违反移动端浏览习惯；列对齐混乱；A11y 差

### 方案 F：用户可切换密度（Density Toggle）

- **核心思路**：在移动端提供"紧凑 / 默认 / 详细"三档切换，存入 localStorage。
- **首屏可见**：紧凑 5–6 张 / 默认 3.5–4 / 详细 2–3 张
- **信息密度**：用户自选
- **实现难度**：**中**（需要 3 套 MobileCard + 切换 UI + 持久化）
- **风险点**：维护成本 × 3；用户可能不知存在此选项

### 方案 G：抽屉式详情（Bottom Sheet on Click）

- **核心思路**：保持极简列表；点击卡片（不是对比按钮）触发 Bottom Sheet 浮层，显示完整指标。
- **首屏可见**：**5–6 张**（卡片 64–80px）
- **信息密度**：列表极简，详情浮层内完整
- **实现难度**：**大**（需要 portal/动画/关闭交互/焦点管理；底部对比条已占用 z-index）
- **风险点**：与现有路由跳转（`router.push('/product/{id}')`）冲突，需要重新定义"点击"

### 方案 H：分组折叠（Grouped Cards by Tier）

- **核心思路**：把模型按"前沿 / 主力 / 其他"三组，组内为紧凑列表，组头可折叠。
- **首屏可见**：**3 组 + 每组 2–3 张**（约 100 + 3×90 = 370px 可放下 3 组的头条 + 1 行）
- **信息密度**：分组后定位更快
- **实现难度**：**大**（与现有 useModelGroups 冲突，排序逻辑需要重设计）
- **风险点**：单组全量的"全表排序"承诺被破坏

## 4. 推荐方案

**推荐：方案 A（紧凑单行卡）作为 Phase 1 实施。**

### 4.1 推荐理由

1. **投入产出比最高**：单文件改 ~80 行，单卡高度从 130–140px → 90–100px（**减约 30%**），首屏多看 1–1.5 张。
2. **风险最低**：保留桌面端、Compare 勾选、路由跳转、a11y label、i18n key 全部不变。
3. **可演进**：Phase 1 跑通后，方案 C（折叠展开）或 D（横向滑动）都能在不破坏 API 的前提下叠加在 Phase 1 之上（即默认紧凑态 = Phase 1，点击展开 = Phase 2 候选）。
4. **不破坏"全表统一排序"承诺**：方案 H、F 都涉及排序/分组逻辑重构，会冲击 useModelGroups 与现有 test/integration。
5. **指标虽然变少但更突出**：智能分从 `text-[11px]` → 提升到 `text-base` 级别显示，反而更易扫读。

### 4.2 Phase 1 设计细节

**新 MobileCard 布局**（90–100px）：

```
┌──────────────────────────────────────────────────┐
│ #1 [L] Model Name                60  $2.50   ☐  │ ← 主行：排名 + logo + 名 + 智能分 + 价格 + 对比
│     company · 开源 · 2024-01              ▸      │ ← 次行：元信息 + 跳转箭头
└──────────────────────────────────────────────────┘
```

- **左**：排名（#1）+ logo + 名字（truncate, max 45%）
- **中右**：智能分（大数字 text-base，带 ▰▰▰▰▱ 短进度条）/ 价格（与智能分同行，弱化）
- **次行**：公司 · type badge · 发布日期 · ArrowUpRight
- **右上**：Compare 勾选（保持 44×44 触摸目标，符合 WCAG）
- **整体点击**：跳转详情（与现状一致）

**新 MOBILE_METRIC_ORDER**（仅在卡片里展示哪些指标）：
- 主指标固定为 `intelligence`（用户最常筛选的指标）
- 次要行内指标固定为 `cost`（用 `blended`，无值显示 `—`）
- tokens / coding / agentic 全部隐去（用户可通过点击进入详情看；或排序时使用 tokens）

**新增 i18n key**：
- `models.expandHint`: "点击查看更多指标"（用于次行 ArrowUpRight 后的 aria-label / title）

### 4.3 高度核算（Phase 1）

| 元素 | 高度 |
|------|-----:|
| 上下 padding (p-2) | 16px |
| 主行（text-base 16/24 + h-4 logo + h-5 compare） | 24px |
| 间距 mt-1 | 4px |
| 次行（text-xs 12/18 + badge text-[10px] py-0） | 18px |
| 1px border × 2 | 2px |
| **小计** | **~64–80px** |
| + space-y-2 (8px) | **72–88px** |

iPhone 14 Pro (852-240) = 612px / 80 = **7.6 张**
iPhone SE (667-240) = 427px / 80 = **5.3 张**

**比现状提升 70–80%**（3.5–4 张 → 5.5–7.5 张）。

> 备注：实际可能比 80px 略高（如果次行 badge 不换行、对比按钮带 44×44 触摸区），按 90–100px 算也已是 4.5–5.5 张。

### 4.4 关键代码改动点

只动 3 个文件：

1. `src/components/ranking-table/mobile-card.tsx` — 重写内部 JSX（保持 props/接口不变）
2. `src/messages/zh.json` + `src/messages/en.json` — 新增 1 个 key（`models.expandHint`）
3. `src/components/ranking-table/MOBILE_DENSITY.md` — 本文件

`index.tsx` 传 `metricOrder` 含义变化但接口保持兼容（cards 内部不再使用 grid 渲染）。

### 4.5 验收标准

- [x] MobileCard 单卡高度 ≤ 100px（含 space-y）
- [x] iPhone 14 Pro (393×852) 视口下首屏可见 ≥ 5 张完整卡片
- [x] Compare 按钮触摸目标 ≥ 44×44px
- [x] 桌面端（≥ 640px）完全不受影响（仍 `hidden sm:block`）
- [x] 所有现有测试通过（vitest + playwright）
- [x] 路由跳转 (`router.push('/product/{id}')`) 行为不变
- [x] 中英文 i18n 同步

## 5. 后续 Phase 路线图

- **Phase 2**：在 Phase 1 基础上叠加方案 C（点击展开次指标），卡片默认紧凑态、点开变 ~170px 显示全部 5+ 指标。
- **Phase 3**：根据实际使用数据（哪些指标在移动端被高频率查询）决定是否需要方案 D（横向滑动）。
- **Phase 4**：考虑方案 F（密度切换）作为 Power User 选项。
